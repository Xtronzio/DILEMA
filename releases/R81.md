# R81 — Validación del contexto por la mesa

Publicado el 1 de octubre de 2026. Frontend: `V0.1.16-010C-R81`.

## Funcionamiento

1. Una persona solicita permiso para proponer contexto. Su solicitud cuenta como SÍ.
2. La mayoría de participantes presentes permite o rechaza la propuesta.
3. Si se permite, la persona escribe hasta 3.000 caracteres y pulsa **PROPONER A LA MESA**.
4. Toda la mesa ve el texto sin identificar a su autor. Se abre una segunda votación independiente. Quien propone el texto ya cuenta como SÍ.
5. Solo la mayoría favorable incorpora ese texto al contexto compartido. Un empate o mayoría negativa lo rechaza.

Durante las tres fases (solicitud, escritura y validación) se mantiene el bloqueo de propuestas concurrentes. El autor puede cancelar; si se ausenta o abandona, la propuesta se cancela. El texto permanece fijo mientras se vota.

Los votos A/B y el ciclo no cambian. El contador de contexto solo aumenta tras la aceptación del texto. El contexto privado sigue siendo editable directamente.

## Ayudas

El contexto pendiente o rechazado nunca se incorpora al contexto utilizado por la IA. La reutilización de guías depende de una firma del contexto aprobado. Una guía anterior se conserva en el historial; al abrir el asistente con un contexto nuevo se prepara una guía para ese contexto usando el acceso ya obtenido. No se sortean herramientas adicionales ni se modifica la mecánica de acceso.

Una generación que llega después de cambiar el contexto o el voto no se guarda como una guía actual. La función `debate-coach` pasa a la versión 12.

## Verificación

- Aprobación, rechazo, empate, cancelación, ausencia y votos tardíos.
- Ningún cambio del contexto compartido durante la escritura o validación.
- Bloqueo de fin, pausa, giro, re-voto, limbo y nuevas solicitudes de contexto mientras hay proceso abierto.
- Las votaciones de permiso y texto no comparten votos; un voto tardío de permiso no cuenta para la validación.
- RPC de validación ejecutado como `authenticated`; participantes ajenos no leen la propuesta. Las tablas de votación privadas no tienen permisos directos para clientes.
- Protección de actualizaciones directas del campo `rounds.context` por clientes.
- Conservación de las guías anteriores y firma de contexto en nuevas guías.
- Pruebas de regresión de R80 (limbo y número de participantes) superadas.
- Los 22 scripts del frontend compilan.

Las pruebas de IA usaron un proveedor simulado y no consumieron tokens reales. Queda la prueba del usuario con varios móviles para verificar interacción y ritmo de lectura.

La revisión de asesores de Supabase conserva avisos anteriores sobre funciones públicas y autenticación anónima. La tabla nueva de votos tiene RLS y acceso directo revocado; la ausencia de políticas es intencional porque solo se usa mediante funciones privadas con comprobación de usuario y sala. Esta versión no es una auditoría global de los permisos heredados.
